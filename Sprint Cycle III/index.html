Three use cases

Three database-supported use cases

These are the three presentation use cases selected in the October 19 Sprint Cycle II meeting notes. They demonstrate database behavior without requiring the Next.js application to implement the workflows.

Run the search and relationship queries and the add/update demonstrations through the README commands. Each mutation example uses BEGIN and ROLLBACK: the inserted/updated rows are real within the transaction, and the original sample data is restored afterward. SQL values use lowercase snake_case, such as creator, visual_art and kept_available.

1. A creator publishes a piece

Goal: A creator publishes writing, visual art or music so other users can discover it and scouts can review the creator’s portfolio.

Part Stored data and relationship
Creator One account row has the Creator role. The person is stored once.
Work A creative_work row stores the creator foreign key, title, media type, description, optional SoundCloud URL, feature/archive flags, publication time and moderation visibility.
Organization Categories and the work-category association relate tags or genres to the work without repeating work rows.
Portfolio A query retrieves works by creator_id. A portfolio is derived from those rows; it is not a second copy of published content.
Discovery A query filters published work by media type and visibility and orders it by publication time.

The database checks the creator relationship, required content and allowed media values. A music work requires a SoundCloud URL. A work cannot reference a nonexistent account. Editing, featuring or archiving updates the same work identifier, which preserves existing comments, review requests and reports.

Presentation sequence: Show a Creator account, show its current portfolio, add a meaningful new work, and retrieve the portfolio again. Explain that only the creative work row was added. Demonstrate a media filter to show how discovery uses the stored media type.

Exact demonstrations: Query Q2 shows Amara Cole’s portfolio. Demo A publishes “Blue hour platform,” revises its title and feature flag, and retrieves the related creator. The public_work_feed view supplies a useful live media/visibility filter for an instructor question.

Application responsibility: Authenticate the user and verify that the signed-in creator is the owner before permitting publication or editing. A foreign key confirms a relationship; it does not establish who is using the browser.

2. A talent scout invites a creator to an opportunity

Goal: A scout finds a suitable creator and offers a commission, exhibition or performance.

Part Stored data and relationship
Search Read Creator accounts using discipline and open_to_commissions, together with their creative works. Search creates no records.
Scout An Account row with the Talent Scout role owns the opportunity.
Opportunity One row stores the scout, title, start/end dates and description. A scout may create many opportunities.
Invitation An associative row links one opportunity to one creator and stores invitation status and time. An opportunity may invite many creators and a creator may receive many opportunities.
Response The invitation’s sent, accepted or declined status records the creator’s response; the same row is updated.
Contact Scout messages retain the conversation or initial contact separately from the invitation relationship.

Foreign keys keep the opportunity and creator references valid. The database prevents duplicate invitations for the same creator and opportunity and rejects invalid status values or reversed opportunity dates. An invitation is the sole relationship between a particular creator and opportunity.

Presentation sequence: Search commission-ready creators, open the results’ portfolio data, show an opportunity owned by a scout, and join the invitation to the opportunity and creator. Explain the unique opportunity/creator pair. Updating a response shows why status is data on the invitation.

Exact demonstrations: Query Q1 finds active music creators accepting commissions. Query Q4 joins opportunities, invitations, scouts and creators. Demo B adds a winter waterfront acoustic opportunity and an invitation, then updates the invitation to accepted with its response time.

Application responsibility: Check the current user’s identity, ownership of the opportunity and permission to send or answer an invitation. Resolve the project’s remaining contact/consent policy before implementing unrestricted messaging.

3. A moderator decides reported creative work

Goal: A community report becomes a moderation case, and the decision is recorded against the original work.

Part Stored data and relationship
Reported work The Creative Work row remains the content identity. Moderation changes its visibility instead of creating another portfolio record.
Work report A report references the work and stores the reason, reporter attribution and report time. One work can have many reports.
Moderation case A trigger automatically creates one moderation_case when a work_report is inserted. It stores the moderator, findings, action, status and recorded time.
Decision The action is kept available, hidden or removed. Case status is open, in review, escalated or closed.
Escalation Serious copyright, fraud or safety concerns can remain linked to the case for administrator review.

The report and case foreign keys preserve the path from decision to report to original creative work. Uniqueness prevents a report from acquiring multiple cases. Database rules restrict action/status values and preserve the decision’s moderator relationship. Administrative bans use the separate account status history rather than a work moderation action.

Presentation sequence: Join a case, report, work, creator and assigned moderator. Modify a case’s findings/action/status, then retrieve the case and the work’s visibility to show the effect. Explain that a work can receive multiple reports, while each report has only one case.

Exact demonstrations: Query Q5 joins reports, cases, creators, works and moderators. Demo C inserts a new report, retrieves the automatically opened case, then records a closed/hidden decision. The closing trigger changes the work’s visibility in the same transaction. An unassigned case may be open; later states require a Moderator account.

Application responsibility: Authenticate the moderator, show only permitted case actions and enforce access to confidential reports. A moderator may warn, restrict or refer a user for a ban. Only an administrator may ban an account.

Relationships to point out during questions

  • One Account to many Creative Works.
  • One Opportunity to many Invitations; one Creator to many Invitations.
  • One Work to many Work Reports; one Work Report to one Moderation Case.
  • Role labels on earlier diagrams are views of Account records, not separate account tables.
  • A database rule proves stored data is consistent. Application authorization proves the acting user is allowed to request the operation.
41 business rules

Business rule enforcement

This register preserves the numbering of all 41 rules in the supplied Sprint II Business Rules workbook. The updated dictionary and schema define the exact implemented structures. “Database” identifies data integrity enforced by PostgreSQL; “Application” identifies a policy that the later application must enforce with the authenticated user.

Database role checks validate the referenced account’s stored role. They do not authenticate the person running SQL. The presentation database owner can inspect and administer the entire database. Production deployment must use restricted application database credentials and application authorization.

SQL uses lowercase snake_case versions of the workbook’s display labels: for example creator, talent_scout, visual_art, in_review, kept_available and refer_for_ban.

No. Supplied rule Enforcement and explanation
1 An account email is unique. Database: unique normalized account email. Application: normalize input before display/sign-in and verify ownership of an email address.
2 An account has one of the five roles. Database: one required role column with allowed values Creator, Mentor, Talent Scout, Moderator or Administrator.
3 Role rectangles describe the same Account identity. Database design: one Account table; role-specific relationships reference its primary key. There are no duplicate Creator/Mentor/Scout person tables.
4 A creative work belongs to one creator. Database: required creator foreign key and Creator-role/ownership validation.
5 A creator can publish many works. Database design: many work rows may share one creator foreign key; that key is not unique in Creative Work.
6 A music piece must have a SoundCloud URL. Database: media-dependent required URL check. Writing and visual art do not require that URL. Application: validate and safely embed external content.
7 Media is Writing, Visual art or Music. Database: required media value restricted to the three supported values.
8 Feature, archive, edit or remove updates the work, not a new portfolio record. Database design: feature/archive/visibility and content fields live on Creative Work; portfolios are queries over creator-owned works. Application: update the existing work identifier.
9 Creators read feedback only about their own work. Application: authorize feedback retrieval using the authenticated creator and the work’s owner. Schema relationships support that filtered query. Database foreign keys alone do not enforce read permissions.
10 A request belongs to one creator, mentor and work. Database: required foreign keys, role checks and validation that the requesting creator owns the work.
11 Creators and mentors may have many requests. Database design: request creator/mentor foreign keys are not individually unique.
12 Request status is waiting, accepted or declined. Database: allowed-value status check.
13 Feedback is stored only for an accepted request. Database: a generated accepted request-status value participates in the composite feedback/request foreign key, preserving both acceptance and matching identity. feedback_requires_accepted_request and answered_request_remains_accepted also provide explicit error checks. Application: expose feedback submission only to the assigned mentor.
14 Feedback includes strengths, improvements and a recommendation. Database: required, nonblank structured feedback fields.
15 Feedback belongs to one work and mentor. Database: foreign keys and matching validation against the referenced request’s work and mentor.
16 Feedback has at most one creator reply. Database: unique feedback foreign key and reply_requires_work_owner ensure one reply with the correct recorded creator. Application: verify the authenticated user matches that creator.
17 A nomination belongs to one mentor and work. Database: required foreign keys and Mentor-role validation.
18 Nomination status is pending, approved or declined. Database: allowed-value status check and decision-field consistency. Application: authorize the moderator’s approval action.
19 Scout search reads discipline, commission availability and works; it inserts no row. Query/application behavior: use SELECT/join/filter over Account and Creative Work. Saving a candidate is a separate explicit operation.
20 A scout message belongs to one scout and creator. Database: required endpoint foreign keys and role checks. Application: authorize the sender and permitted conversation participants.
21 An opportunity belongs to one scout. Database: required scout foreign key with Talent Scout-role validation.
22 Invitation alone links opportunity and creator; the same pair occurs once. Database: required opportunity/creator foreign keys and unique opportunity/creator pair.
23 Invitation status is sent, accepted or declined. Database: allowed-value status check. Application: the invited creator controls the response.
24 A work report belongs to one work; one work may have many reports. Database: required work foreign key; it is not unique in Work Report.
25 One work report opens one moderation case. Database: work_report_opens_case creates the case after report insertion. A unique report foreign key prevents duplicates, and deferred constraint triggers prevent a report from losing its case.
26 A case records findings, action and open/in review/escalated/closed status. Database: nonblank findings, allowed status/action checks, moderator assignment after the open state, and a required reason for escalation. New cases use Awaiting review until findings are entered. Application: ensure findings substantively justify the decision.
27 Work action is kept available, hidden or removed. Database: allowed action values; closed_case_applies_visibility changes the associated work or comment visibility when a case closes.
28 A user report belongs to one account. Database: required reported-account foreign key.
29 A moderator may warn, restrict or refer for ban. Database: Moderator-role relationship and allowed restriction action values. Application: authenticate the moderator and enforce policy/duration.
30 Moderators do not ban; bans are administrator changes. Database: ban state uses the administrator status-change workflow. Application/database grants: prevent a moderator from invoking administrator operations or directly updating account status.
31 Administrators activate, suspend, ban or deactivate accounts. Database: allowed account status values and Administrator-role validation for recorded status changes. Application: authenticate and authorize the administrator.
32 Each action updates current account status and stores one Status Change. Database: status_change_updates_account locks and updates the target account during audit insertion, capturing its old status. account_status_requires_audit rejects direct status updates; status_history_append_only rejects audit updates/deletion. Application: authorize the acting administrator.
33 Applications request Mentor or Talent Scout, not Creator. Database: requested-role check allows those specialized roles only. Creator registration remains separate.
34 Application status is pending, accepted or rejected. Database: allowed-value status check and required/nullable decision metadata according to status.
35 An accepted application allows Mentor/Scout account use. Database: deferred constraint triggers require every Mentor/Scout account to have an accepted application matching its account ID, canonical email and role at transaction commit. Application: authenticate the approved user and check account status before access.
36 Analytics retain report type and selected start/end dates. Database: required report type, date range and generator relationship; chronological date check. Queries compute results from stored application data.

Details that change the original dictionary

  • SQL role, media and status labels use lowercase snake_case. For example, “Talent Scout” becomes talent_scout, “Visual art” becomes visual_art, “in review” becomes in_review, and “kept available” becomes kept_available.
  • Account identifiers use PostgreSQL identity-backed bigint keys. The dictionary’s generic DateTime becomes timestamptz; opportunity/report periods use date.
  • Generated role columns let composite foreign keys enforce that a referenced account is the required Creator, Mentor, Scout, Moderator or Administrator. They are database-maintained integrity fields rather than duplicate people.
  • creative_work.content_text stores writing itself. work_media stores ordered external asset URLs and alternative text for images or other media. This sprint does not claim an implemented upload/storage service.
  • creative_work.featured remains the creator’s portfolio selection. An approved nomination supplies the community featured feed; the two meanings remain distinct.
  • The feedback/request composite foreign key includes a generated accepted status, the work and the mentor. Accepted status is therefore part of the stored relationship, alongside triggers with readable error messages. feedback_reply.creator_id explicitly identifies the reply author; a trigger verifies that account owns the reviewed work, and uniqueness allows only one reply per feedback.
  • Each inserted work or comment report automatically opens its case. A case targets exactly one work report or comment report, and deferred checks prevent an existing report from losing its case.
  • moderation_case.moderator_id is nullable for an unassigned open case, unlike the source dictionary’s always-required field. Any later case state requires a moderator. Findings default to Awaiting review; escalated cases require an explanation. Closing a case applies its action to work/comment visibility.
  • Inserting status_change captures the old status, locks and updates the account, and stores the audit row in the same transaction. Direct account-status changes and audit update/deletion are rejected.
  • An accepted specialized-role application and its Mentor/Scout account must be created in the same transaction. Deferred checks require the accepted application, canonical email, requested role and approved account to match at commit.
  • Invitations store responded_at. An acceptance or decline must include that timestamp; checks preserve chronological consistency.
  • Temporary restrictions have an expiry, and support tickets gain assignment, response and resolution metadata. The application must honor these stored values.

Sprint III follows that later database rule. Administrator and Moderator provisioning remains an authorized staff workflow rather than public self-selection.

CREATE SCHEMA xpression;
SET search_path TO xpression, public;

CREATE TABLE account (
    account_id bigint GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    name text NOT NULL CHECK (btrim(name) <> ''),
    email text NOT NULL CHECK (email = lower(btrim(email)) AND email ~ '^[^[:space:]@]+@[^[:space:]@]+\.[^[:space:]@]+$'),
    role text NOT NULL CHECK (role IN ('creator','mentor','talent_scout','moderator','administrator')),
    status text NOT NULL DEFAULT 'active' CHECK (status IN ('active','suspended','banned','deactivated')),
    discipline text,
    open_to_commissions boolean NOT NULL DEFAULT false,
    password_hash text NOT NULL CHECK (btrim(password_hash) <> ''),
    bio text,
    created_at timestamptz NOT NULL DEFAULT CURRENT_TIMESTAMP,
    CONSTRAINT account_email_key UNIQUE (email),
    CONSTRAINT account_id_role_key UNIQUE (account_id,role),
    CONSTRAINT account_commissions_creator CHECK (NOT open_to_commissions OR role = 'creator')
);

CREATE TABLE role_application (
    application_id bigint GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    administrator_id bigint,
    administrator_role text GENERATED ALWAYS AS ('administrator'::text) STORED,
    applicant_name text NOT NULL CHECK (btrim(applicant_name) <> ''),
    email text NOT NULL CHECK (email = lower(btrim(email)) AND email ~ '^[^[:space:]@]+@[^[:space:]@]+\.[^[:space:]@]+$'),
    requested_role text NOT NULL CHECK (requested_role IN ('mentor','talent_scout')),
    statement text NOT NULL CHECK (btrim(statement) <> ''),
    status text NOT NULL DEFAULT 'pending' CHECK (status IN ('pending','accepted','rejected')),
    submitted_at timestamptz NOT NULL DEFAULT CURRENT_TIMESTAMP,
    decided_at timestamptz,
    approved_account_id bigint UNIQUE,
    CONSTRAINT application_admin_fk FOREIGN KEY (administrator_id,administrator_role) REFERENCES account(account_id,role),
    CONSTRAINT application_approved_role_fk FOREIGN KEY (approved_account_id,requested_role) REFERENCES account(account_id,role),
    CONSTRAINT application_decision_check CHECK (
      (status = 'pending' AND administrator_id IS NULL AND decided_at IS NULL AND approved_account_id IS NULL)
      OR (status = 'rejected' AND administrator_id IS NOT NULL AND decided_at IS NOT NULL AND approved_account_id IS NULL)
      OR (status = 'accepted' AND administrator_id IS NOT NULL AND decided_at IS NOT NULL AND approved_account_id IS NOT NULL)),
    CONSTRAINT application_dates_check CHECK (decided_at IS NULL OR decided_at >= submitted_at)
);

    work_id bigint GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,

-- Cross-row integrity. These are integrity rules; they do not identify the signed-in user.
CREATE FUNCTION assert_specialized_approval(target_id bigint) RETURNS void
LANGUAGE plpgsql SET search_path = xpression, pg_temp AS $$
DECLARE a account%ROWTYPE;
BEGIN
    SELECT * INTO a FROM account WHERE account_id = target_id;
    IF FOUND AND a.role IN ('mentor','talent_scout') AND NOT EXISTS (
      SELECT 1 FROM role_application ra WHERE ra.approved_account_id = a.account_id
        AND ra.status = 'accepted' AND ra.requested_role = a.role AND ra.email = a.email) THEN
        RAISE EXCEPTION 'Specialized account % requires an accepted matching role application', target_id
          USING ERRCODE = '23514', CONSTRAINT = 'specialized_account_approval';
    END IF;
END;
$$;

CREATE FUNCTION check_specialized_approval() RETURNS trigger
LANGUAGE plpgsql SET search_path = xpression, pg_temp AS $$
BEGIN
    IF TG_TABLE_NAME = 'account' THEN
        PERFORM assert_specialized_approval(NEW.account_id);
    ELSE
        IF TG_OP <> 'INSERT' AND OLD.approved_account_id IS NOT NULL THEN
            PERFORM assert_specialized_approval(OLD.approved_account_id);
        END IF;
        IF TG_OP <> 'DELETE' AND NEW.approved_account_id IS NOT NULL THEN
            PERFORM assert_specialized_approval(NEW.approved_account_id);
        END IF;
    END IF;
    RETURN NULL;
END;
$$;

CREATE CONSTRAINT TRIGGER account_specialized_approval
AFTER INSERT OR UPDATE ON account DEFERRABLE INITIALLY DEFERRED
FOR EACH ROW EXECUTE FUNCTION check_specialized_approval();
CREATE CONSTRAINT TRIGGER application_specialized_approval
AFTER INSERT OR UPDATE OR DELETE ON role_application DEFERRABLE INITIALLY DEFERRED
FOR EACH ROW EXECUTE FUNCTION check_specialized_approval();

CREATE FUNCTION check_feedback_request_accepted() RETURNS trigger

DECLARE request_status text;

CREATE FUNCTION open_report_case() RETURNS trigger

CREATE FUNCTION require_report_case() RETURNS trigger
LANGUAGE plpgsql SET search_path = xpression, pg_temp AS $$
BEGIN
    IF TG_TABLE_NAME = 'work_report' THEN
        IF EXISTS (SELECT 1 FROM work_report WHERE report_id = NEW.report_id) AND
          NOT EXISTS (SELECT 1 FROM moderation_case WHERE report_id = NEW.report_id) THEN
            RAISE EXCEPTION 'Every work report requires exactly one moderation case' USING ERRCODE = '23514';
        END IF;
    ELSIF TG_TABLE_NAME = 'comment_report' THEN
        IF EXISTS (SELECT 1 FROM comment_report WHERE comment_report_id = NEW.comment_report_id) AND
          NOT EXISTS (SELECT 1 FROM moderation_case WHERE comment_report_id = NEW.comment_report_id) THEN
            RAISE EXCEPTION 'Every comment report requires exactly one moderation case' USING ERRCODE = '23514';
        END IF;
    ELSE
        IF OLD.report_id IS NOT NULL AND EXISTS (SELECT 1 FROM work_report WHERE report_id = OLD.report_id) AND
          NOT EXISTS (SELECT 1 FROM moderation_case WHERE report_id = OLD.report_id) THEN
            RAISE EXCEPTION 'A work report cannot lose its moderation case' USING ERRCODE = '23514';
        END IF;
        IF OLD.comment_report_id IS NOT NULL AND EXISTS (SELECT 1 FROM comment_report WHERE comment_report_id = OLD.comment_report_id) AND
          NOT EXISTS (SELECT 1 FROM moderation_case WHERE comment_report_id = OLD.comment_report_id) THEN
            RAISE EXCEPTION 'A comment report cannot lose its moderation case' USING ERRCODE = '23514';
        END IF;
    END IF;
    RETURN NULL;
END;
$$;
CREATE CONSTRAINT TRIGGER work_report_requires_case AFTER INSERT OR UPDATE ON work_report
DEFERRABLE INITIALLY DEFERRED FOR EACH ROW EXECUTE FUNCTION require_report_case();
CREATE CONSTRAINT TRIGGER comment_report_requires_case AFTER INSERT OR UPDATE ON comment_report
DEFERRABLE INITIALLY DEFERRED FOR EACH ROW EXECUTE FUNCTION require_report_case();
CREATE CONSTRAINT TRIGGER moderation_case_cannot_orphan_report AFTER UPDATE OR DELETE ON moderation_case
DEFERRABLE INITIALLY DEFERRED FOR EACH ROW EXECUTE FUNCTION require_report_case();

CREATE FUNCTION apply_moderation_decision() RETURNS trigger
LANGUAGE plpgsql SET search_path = xpression, pg_temp AS $$
DECLARE new_visibility text;
BEGIN
    IF NEW.status = 'closed' THEN
        new_visibility := CASE WHEN NEW.action_taken = 'kept_available' THEN 'available' ELSE NEW.action_taken END;
        IF NEW.report_id IS NOT NULL THEN
            UPDATE creative_work SET visibility = new_visibility
              WHERE work_id = (SELECT work_id FROM work_report WHERE report_id = NEW.report_id);
        ELSE
            UPDATE comment SET visibility = new_visibility
              WHERE comment_id = (SELECT comment_id FROM comment_report WHERE comment_report_id = NEW.comment_report_id);
        END IF;
    END IF;
    RETURN NEW;
END;
$$;
CREATE TRIGGER closed_case_applies_visibility AFTER INSERT OR UPDATE ON moderation_case
FOR EACH ROW EXECUTE FUNCTION apply_moderation_decision();

CREATE FUNCTION protect_account_status() RETURNS trigger
LANGUAGE plpgsql SET search_path = xpression, pg_temp AS $$
BEGIN
    IF TG_OP = 'INSERT' THEN
        IF NEW.status <> 'active' THEN
            RAISE EXCEPTION 'New accounts start active; insert a status_change for later actions' USING ERRCODE = '23514';
        END IF;
    ELSIF NEW.status IS DISTINCT FROM OLD.status AND pg_trigger_depth() < 2 THEN
        RAISE EXCEPTION 'Change status by inserting status_change; direct status updates are not allowed' USING ERRCODE = '23514';
    END IF;
    RETURN NEW;
END;
$$;
CREATE TRIGGER account_status_requires_audit BEFORE INSERT OR UPDATE OF status ON account
FOR EACH ROW EXECUTE FUNCTION protect_account_status();

CREATE FUNCTION apply_status_change() RETURNS trigger
LANGUAGE plpgsql SET search_path = xpression, pg_temp AS $$
DECLARE previous_status text;
BEGIN
    SELECT status INTO previous_status FROM account WHERE account_id = NEW.account_id FOR UPDATE;
    IF NOT FOUND THEN RAISE EXCEPTION 'Target account does not exist' USING ERRCODE = '23503'; END IF;
    IF NEW.new_status = previous_status THEN
        RAISE EXCEPTION 'New status must differ from the existing status' USING ERRCODE = '23514';
    END IF;
    NEW.old_status := previous_status;
    UPDATE account SET status = NEW.new_status WHERE account_id = NEW.account_id;
    RETURN NEW;
END;
$$;
CREATE TRIGGER status_change_updates_account BEFORE INSERT ON status_change
FOR EACH ROW EXECUTE FUNCTION apply_status_change();

END;
$$;

-- Safe projection for presentation/public listings. This is not an authorization boundary.
CREATE VIEW public_work_feed AS
SELECT cw.work_id,cw.creator_id,a.name AS creator_name,cw.title,cw.media_type,cw.description,
       cw.soundcloud_url,cw.content_text,cw.published_at,
       EXISTS (SELECT 1 FROM nomination n WHERE n.work_id = cw.work_id AND n.status = 'approved') AS community_featured
FROM creative_work cw JOIN account a ON a.account_id = cw.creator_id
WHERE cw.visibility = 'available' AND NOT cw.archived AND a.status = 'active';

CREATE VIEW scout_creator_directory AS
SELECT a.account_id AS creator_id,a.name,a.discipline,a.open_to_commissions,a.bio,
       count(cw.work_id) AS visible_work_count
FROM account a LEFT JOIN creative_work cw
  ON cw.creator_id = a.account_id AND cw.visibility = 'available' AND NOT cw.archived
WHERE a.role = 'creator' AND a.status = 'active'
GROUP BY a.account_id,a.name,a.discipline,a.open_to_commissions,a.bio;

CREATE VIEW moderation_queue AS
SELECT mc.case_id,mc.report_id,mc.comment_report_id,mc.moderator_id,mc.status,
       coalesce(wr.reason,cr.reason) AS report_reason,wr.reason_type,
       coalesce(wr.reported_at,cr.reported_at) AS reported_at,
       coalesce(wr.work_id,c.work_id) AS work_id
FROM moderation_case mc
LEFT JOIN work_report wr ON wr.report_id = mc.report_id
LEFT JOIN comment_report cr ON cr.comment_report_id = mc.comment_report_id
LEFT JOIN comment c ON c.comment_id = cr.comment_id;

  AND a.discipline ILIKE '%music%'
  AND NOT w.archived
  AND w.visibility = 'available'

ORDER BY a.name;

-- Real PostgreSQL integration checks, including expected constraint failures.
-- Every write below is temporary. Any failed assertion stops psql with a nonzero exit.
BEGIN;
SET CONSTRAINTS ALL IMMEDIATE;
CREATE TEMP TABLE verification_result (
    test_name text PRIMARY KEY,
    result text NOT NULL,
    detail text NOT NULL
) ON COMMIT DROP;

CREATE FUNCTION pg_temp.assert_true(test_name text, passed boolean, detail text DEFAULT '')
RETURNS void LANGUAGE plpgsql AS $function$
BEGIN
    IF passed IS DISTINCT FROM true THEN
        RAISE EXCEPTION 'FAIL: % | %', test_name, detail;
    END IF;
    INSERT INTO verification_result VALUES (test_name, 'PASS', detail);
END;
$function$;

CREATE FUNCTION pg_temp.expect_error(test_name text, command text, expected_state text)
RETURNS void LANGUAGE plpgsql AS $function$
DECLARE failed boolean := false; actual_state text; constraint_detail text;
BEGIN
    -- A PL/pgSQL exception block is a subtransaction. Rejected writes roll back.
    BEGIN
        EXECUTE command;
    EXCEPTION WHEN OTHERS THEN
        GET STACKED DIAGNOSTICS actual_state = RETURNED_SQLSTATE,
                                constraint_detail = CONSTRAINT_NAME;
        IF actual_state <> expected_state THEN
            RAISE EXCEPTION 'FAIL: % expected SQLSTATE %, received %: %',
                test_name, expected_state, actual_state, SQLERRM;
        END IF;
        failed := true;
        INSERT INTO verification_result
        VALUES (test_name, 'PASS', 'Rejected with SQLSTATE ' || actual_state ||
                CASE WHEN constraint_detail <> '' THEN ' (' || constraint_detail || ')' ELSE '' END);
    END;
    IF NOT failed THEN
        RAISE EXCEPTION 'FAIL: % unexpectedly accepted invalid data', test_name;
    END IF;
END;
$function$;
