Sprint Cycle I – User Interface Design

Deliverable:
User Interface Design and Initial Application Screen


Purpose

The purpose of this sprint cycle is to design the user interface for the application before major implementation begins.

The team will use the Functional Requirements document to determine:

- what screens are needed,
- what information each screen should display,
- what actions users should be able to perform,
- and how the interface supports the required use cases.

The team will also implement one very small screen in the actual application to verify that the selected programming language, framework, IDE, and GitHub workflow are functioning correctly.

Most of the application functionality will NOT be implemented during this sprint.


1. Design the Sign-In Screen

Create the sign-in screen for the application.

You may also design related screens such as:

- Registration
- Forgot Password
- Account Creation

if these are required by your system.

The system will eventually determine the user's role after sign-in and display the appropriate navigation and functionality.


2. Design the Role-Based Landing/Navigation Screens

Design the landing or navigation screen for EACH system role.

Each landing page should clearly show the major functions available to that role.

Example:

Campus User

- Browse Items
- List an Item
- My Reservations
- My Listings

Administrator

- Manage Users
- Manage Categories
- Review Reports
- Generate Reports

The options do not need to work during this sprint.


3. Design Screens for Two Use Cases for Each Role

For each role, select TWO meaningful use cases from the Functional Requirements document and design the screens needed to support those use cases.

Try to choose use cases that require different types of screens.

For example, do not choose a Browse/Search use case for every role.

Across the different roles, try to include a variety of screen types such as:

- Browse/Search
- Detail View
- Create/Add Form
- Modify/Update Form
- Approval/Review
- Report
- Dashboard
- Messaging
- Scheduling
- Profile
- Moderation
- Analytics

Example:

Role: Campus User

Use Case 1: Search Available Items
Possible Screens:
- Browse Items
- Item Details

Use Case 2: List an Item
Possible Screens:
- Create Item Listing
- Listing Confirmation


Role: Administrator

Use Case 1: Manage Users
Possible Screens:
- User Search
- User Details

Use Case 2: Generate System Report
Possible Screens:
- Report Criteria
- Report Results

The purpose is to show meaningful variation in the application's interface and to make sure the UI supports different kinds of functionality.


4. Implement a Simple Application Splash/Home Screen

Using the programming language, framework, IDE, and development tools selected by the team, implement a simple application screen.

The screen should display:

- Application name
- Application logo or placeholder graphic
- Short project description or tagline
- Basic navigation placeholder

For example, the navigation could include placeholders for:

- Login
- Contact Us
- About
- Help
- Other appropriate navigation for your application

The links or buttons do NOT need to work.

This screen does NOT need to:

- connect to the database,
- authenticate users,
- implement user roles,
- implement use cases,
- or provide working application functionality.

The purpose of this implementation is to verify that:

- the selected development environment works,
- the team can build and run the application,
- the team understands the basic project structure,
- the code can be pushed to GitHub,
- and other team members can pull and run the application.

This is NOT the implementation of the complete user interface designed in this sprint.

It is only a small technical proof that the team's programming language, framework, IDE, and repository workflow are working correctly.


GitHub Requirement

All Sprint Cycle I materials and the splash/home screen code must be stored in the team's GitHub repository.

This includes:

- Sign-In Screen
- Role Landing/Navigation Screens
- Screen mockups for the selected use cases
- Splash/Home Screen source code

Each team member must make at least one meaningful contribution during the sprint and push that contribution to GitHub.

Every team member should also pull the current repository and verify that the application runs in their development environment.


Sprint Cycle I Presentation

During the presentation, the team must:

1. Briefly explain the overall user-interface approach.

2. Show the sign-in screen.

3. Show the landing/navigation screen for each role.

4. For each role, show the screens designed for the TWO selected use cases.

5. Explain why the selected use cases represent different types of functionality where possible.

6. Explain how the screens support the Functional Requirements.

7. Run the implemented splash/home screen from the application.

8. Show that the splash/home screen code is stored in GitHub.

9. Show that the Sprint Cycle I materials are stored in GitHub.

The major application functionality does NOT need to work during this presentation.


Team Organization

Choose a Scrum Master for this Sprint Cycle.

The Scrum Master will:

- coordinate team meetings,
- track progress,
- record important decisions,
- communicate questions to the instructor,
- and coordinate the presentation.

The Scrum Master is NOT responsible for creating all of the deliverables.

All team members are expected to participate in the design and development activities.

Maintain the required meeting documentation throughout the sprint.

Meetings should be spread throughout the sprint and should not all occur near the deadline.


Sprint Cycle I Submission

Submit:

- Sign-In Screen
- Role Landing/Navigation Screens
- Screens for TWO selected use cases for each role
- Splash/Home Screen source code in GitHub
- GitHub repository link
- Presentation
- Required meeting documentation


Important

You may use any tool to design the your screens

Do not implement any application functionality during this sprint.

The primary goal of Sprint Cycle I is to design representative user-interface screens for the application's major roles and use cases.

The small splash/home screen implementation is included only to verify that the team's development technology and GitHub workflow are working correctly.
